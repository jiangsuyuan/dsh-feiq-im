# dsh-feiq-im · 飞秋兼容的 DSH 局域网 IM 设计方案

> 状态：已定稿（待实施）｜ 包名 `dsh-feiq-im` ｜ 目标：气泡常驻 + 零添加 + 送达/已读，并兼容飞秋 / 飞鸽（IPMsg） ｜ 基线：DSH Desktop `0.2.2-rc.5`（profile `desktop`）

![界面方案示意](design-ui.svg)

---

## 1. 问题拆解：现状为什么难用

你现在的痛点是四条，恰好对应 `dsh-lan-chat` 的四个设计选择（已读取其安装产物核实）：

| 你的痛点 | 现状实现（`dsh-lan-chat` 2.2.2） | 后果 |
| --- | --- | --- |
| 入口在左侧上部，不在工作区 | 客户端注册了 `main`（主面板 key）+ `sidebar.panellist`（左侧图标） | 必须切走整个工作区才能看消息；不在那个面板时，消息来了完全没感知 |
| 不能像 FeiQ 那样自动发现、还要加好友 | 有 UDP 广播 + 网段扫描，但"发现"是第三个页签，扫到的人要**一键添加**才进联系人 | 新人上线不出现、不提醒；本质仍是"加好友"模型 |
| 来新消息没有提示 | 未读只显示在那个面板的会话列表里 | 没有全局角标、没有红点、没有常驻入口 |
| 送达 / 未读已读不直观 | 只有"发送成功/失败"和会话级已读位置，没有逐条回执 | 发出去后不知道对方收没收到、看没看 |

结论：不是缺功能，是**入口位置 + 名册模型 + 回执模型**三件事选错了。本方案只改这三件，其余能复用就复用。

**验收一句话**：同事开机 5 秒内自动出现在你的在线列表里，你点一下就发消息；任何面板下右侧都有气泡，来消息红点数字跳动；发出去的每条消息下面都有"已送达 / 已读"。

## 2. 方案结论（先给答案）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 改造还是新建 | **新建独立插件 `dsh-feiq-im`** | 现有包是 market 上的 `dsh-lan-chat`，改包名外的行为会和上游升级冲突；且要删掉它唯一的入口（左栏面板），等于换了个壳 |
| 网络层 | **IPMsg 兼容层为主 + 自研 v1 扩展**：发现/文本走 UDP 2425，文件走 TCP 2425，群聊/离线/加密走自有 HTTP（45891） | 互通是落地关键——同事不装插件也能聊；v1 只补 IPMsg 没有的能力 |
| 入口 | 只注册 **`shell.overlay`** 一个气泡 + 浮层，**不注册** `main` / `sidebar.panellist` | `shell.overlay` 是框架级浮层，位于所有分栏之上、滚动容器之外——`dsh-deepseek-meter` 就是这么挂的，你在用它且满意 |
| 名册 | **发现即名册**：上线即出现，离线变灰，零"添加"动作 | 与飞秋同一来源（IPMsg 广播）；单聊会话在首次发消息时惰性创建 |
| 回执 | 逐条 `sent → delivered → read`：收到 `RECVMSG` 即送达，收到 `READMSG` 即已读 | 与飞秋原生语义对齐，不自己发明一套 |
| 对端通道 | UDP/TCP **2425**（IPMsg）+ **45891**（v1 扩展） | 一条防火墙规则覆盖飞鸽/飞秋/本插件；扩展通道只在双方都装本插件时启用 |
| 与现有插件共存 | 建议**停用** `dsh-lan-chat` | 两者默认端口不同、不会直接抢端口，但两套发现协议互不识别，双开只会白耗广播、让人误判"对方在线"，且协议不互通 |

## 3. 总体架构

```
┌────────────────────────── 你的浏览器窗口（DSH Web 页面）──────────────────────────┐
│  shell.overlay 里的气泡 + 浮层（本插件客户端半侧）                                  │
│        │  EventSource /feiq-im/stream        ▲  POST /feiq-im/api/*               │
│        ▼                                    │                                    │
│  DSH Web Server（仅回环）──────────────►  宿主半侧 dsh-feiq-im（Node 主进程）        │
│                                              │  ├─ 状态机 / 会话 / 未读 / 回执     │
│                                              │  ├─ store（JSONL + 附件）          │
│                                              │  ├─ UDP :2425  IPMsg 发现 + 文本   │
│                                              │  ├─ TCP :2425  文件（飞鸽标准）    │
│                                              │  └─ HTTP :45891 v1 扩展（可选）    │
└──────────────────────────────────────────────┼────────────────────────────────────┘
                                               │ 局域网
                          ┌────────────────────┴────────────────────┐
                          ▼                                         ▼
              ┌───────────────────────┐                 ┌───────────────────────┐
              │ 同事的飞秋 / 飞鸽      │                 │ 同事的 dsh-feiq-im    │
              └───────────────────────┘                 └───────────────────────┘
```

三层职责：

1. **宿主半侧**是唯一事实源：名册、会话、消息、回执、未读计数都在这里，进程重启不丢。
2. **浏览器半侧**只是它的一个视图：SSE 收增量，POST 发命令，自己只保留"面板开没开、Draft、滚动位置"这类视图态。
3. **对端**只跑宿主半侧，跟界面无关——所以 DSH 没开窗口时照样能收消息、回回执。

## 4. 界面设计

### 4.1 气泡（常驻、唯一入口）

| 项 | 规格 |
| --- | --- |
| 槽位 | `shell.overlay`（`list`，root 作用域；注册项 `id` 必填，`order` 可选） |
| 位置 | `position: fixed; right: 16px; top: 50%; translateY(-50%)`——**右侧垂直居中** |
| 为什么不在右下角 | `dsh-deepseek-meter` 已经占了 `right:16 / bottom:16`；居中可以两者共存（见示意图①） |
| 尺寸 | 48×48 圆形；比 meter 的胶囊略大，作为主入口更醒目 |
| 常态 | 白底（`--dsw-alias-bg-overlay`）+ 细边（`--dsw-alias-border-l1`）+ 轻投影 + 对话图标 |
| 有未读 | 右上角红色角标：`--dsw-alias-state-error-primary` 底、白字、11px/700、最小 20px；`>99` 显示 `99+`；数字变化时 200ms 缩放强调（`prefers-reduced-motion` 下关闭） |
| 无未读 | 只有图标；不显示"0" |
| 在线状态 | 图标右下 8px 绿点（`--dsw-alias-state-success-primary`）表示"本机监听正常"；监听失败变红点并在面板顶部说明原因 |
| 悬停 | `--dsw-alias-border-l2` 描边 + Tooltip「局域网聊天 · 3 条未读」 |
| 点击 | 打开/收起浮层；**有未读时直接落在「未读」列表** |
| 键盘 | `Enter/Space` 打开；`Esc` 关闭并把焦点还给气泡；`aria-haspopup="dialog"`、`aria-expanded`、`aria-label` 带未读数 |

### 4.2 浮层（点开之后）

| 项 | 规格 |
| --- | --- |
| 形态 | 从气泡左侧展开的浮层面板：`360 × min(560, 76vh)`，圆角 12，`--dsw-alias-bg-overlay`，`backdrop-filter: blur(8px)`，投影 |
| 定位 | `right: 76px`（16 + 48 + 12），与气泡垂直居中对齐 |
| 关闭 | 点浮层外部、点气泡、`Esc`；打开时焦点进入输入框 |
| 两种视图 | 列表视图 ⇄ 会话视图（drill-in，带返回箭头），不做页签 |
| 状态保持 | 关闭不销毁数据；再次打开**默认回到未读列表**（没有未读时回到上次会话），不记忆滚动位置 |

**列表视图分区（关键：这就是"谁发了消息"）**

```
未读 · 3                ← 有未读才出现，按最近一条时间倒序
  老王  文件放哪了？      2   ◀ 红色计数与气泡角标同色
  小李  在吗             1
在线同事 · 2            ← 所有被发现且在线、无未读的人，按昵称排序
  张工  192.168.1.18 · 未聊过     ●
  阿May 192.168.1.31 · 未聊过     ●
最近会话                ← 已读的历史会话（最多 20 条，P1 加"全部"）
── 我 · PC-01 · 192.168.1.23   ⚙
```

- **在线同事**是 FeiQ 的核心：不需要任何"添加"，人一上线就在这；点一下直接开空白会话发消息。
- 未读行用 `--dsw-alias-brand-primary` 极淡底 + 未读数字胶囊；已读行纯文字。
- 未读数字与气泡角标同源（主机端算好总数推给前端），不会对不上。

### 4.3 会话视图

| 区域 | 内容 |
| --- | --- |
| 头部 | `‹` 返回、头像、昵称、状态（`在线` / `最后在线 12:03` / `对方版本过低`），右侧最后一条的 `已读/未读` 汇总 |
| 消息区 | 自己的靠右品牌色气泡；对方的靠左中性底（`--dsw-alias-bg-layer-2`）；日期分隔线；**首次打开时"以下为新消息"分割线** |
| 逐条状态（只在自己的气泡下） | `发送中` 转圈 ｜ `已送达` 单勾 `✓` ｜ `已读` 双勾 `✓✓`（品牌色）｜ `失败` 红 `!` + 整行可点重试 |
| 输入区 | 多行输入（1–4 行自适应），`Enter` 发送 / `Shift+Enter` 换行，右侧发送按钮；空内容禁用 |
| 空态 | 新会话显示「你正在与 XX 直接对话 · 消息只经过你们两台机器」 |

### 4.4 视觉与主题

只用框架 token，明暗自动跟随（不写死颜色）：

| 用途 | Token |
| --- | --- |
| 浮层 / 气泡底 | `--dsw-alias-bg-overlay` |
| 嵌套面（对方气泡、输入框） | `--dsw-alias-bg-layer-2` |

字号对齐宿主：面板标题 15/700、行标题 13、摘要 11、元信息 10–11。不改 `document.title`、不动侧栏 DOM。

## 5. 自动发现与在线名册

发现直接**复用 IPMsg 的广播**（见附录 B），不再自研发现协议：

```text
启动 / 每 10s / 网卡变化 ──► 广播 BR_ENTRY 0x1 ──► 别人立刻出现在我名单里
收到别人的 BR_ENTRY ──► 回 ANSENTRY 0x3 ──► 我立刻出现在别人名单里
收到 BR_EXIT / 30s 无包 ──► 灰显离线
```

- **零添加**：名册就是"谁在广播"，和飞秋的在线列表同一来源。
- **身份**：内部会话键用 IPMsg 的 `user@host`（昵称 + 主机名），IP 只当"地址"——换 DHCP 地址不丢历史。若两台机器 `user@host` 相同，追加 IP 后缀区分。
- **飞秋按源 IP 认设备**：同一 IP 只会被它当成一台机器。所以本插件与飞秋**不能同时开在同一台机器上**（不仅是端口冲突，还是身份冲突）。
- **周期**：BR_ENTRY 每 10s（±1s 抖动）；TTL 30s（3 个周期）。

### 5.2 兜底

1. 广播被防火墙拦 → 对指定 IP **单播** `BR_ENTRY`，收到 `ANSENTRY` 即入名册（等价于飞秋的"按 IP 添加"）。
2. 整段扫描：/24 内限速单播 `BR_ENTRY`（48 并发、700ms 超时、上限 1024 地址），把回包的机器并入名册。
3. AP 隔离 / 跨网段：明确提示"双方不在同一广播域"，不假装在工作。

## 6. 消息、送达与已读

### 6.1 数据模型

```ts
Peer   { key: 'user@host', nick, host, ip, port, proto: 'ipmsg'|'v1', lastSeenAt, online }
Conv   { id, peerKey, unread, lastMsgId, lastAt, blocked }
Msg    { id, convId, from, to, seq, ts, kind: 'text'|'file'|'system',
         body, status, deliveredAt?, readAt?, file? }
```

- `convId` 用 `peerKey`（`user@host`），IP 只作地址；同名机器再加 IP 后缀。
- `seq` = 发送方在该会话内的自增序号，用于回执游标；`id` 用于幂等去重。
- `status` 是**发送方视角**：`queued | sending | delivered | read | failed`。

### 6.2 状态机

```
queued ──发出──► sending ──收到 RECVMSG──► delivered ──收到 READMSG──► read
   ▲                │
   │                └──8s 无回执 / 发送报错──► failed ──点重试──► sending
   └──────────────── 重启恢复：sending 一律回落 queued 并自动重发一次
```

- **送达 = 对方回 `RECVMSG`**（仅当我们发时带了 `SENDCHECK`），不是"本地 socket 写成功"。UDP 是发出去就不管，所以**没有回执就永远是"发送中"**。
- **已读 = 对方回 `READMSG`**，它只在我们带了 `READCHECK`、且对方真的把窗口打开时才发。老客户端不回，就停在"已送达"。
- v1 通道（7.3）里两者分别映射为"HTTP 200"和"read 帧"，状态机与 UI 完全一样。
- 发送方收到回执只记 `peerReadUpTo[convId]` 与 `deliveredSet`，渲染时 `msg.seq <= peerReadUpTo` 即双勾；不逐条存，省空间也不会漏。

### 6.3 未读规则（前端与主机端一致）

| 场景 | 未读 |
| --- | --- |
| 不在该会话 | +1，总数 +1，气泡角标更新 |
| 正在该会话且窗口有焦点且滚到底 | 不入未读，直接上报已读 |
| 正在该会话但窗口失焦 / 滚到上面看历史 | +1，顶部悬浮"3 条新消息"条，点击回底 |
| 面板整体关闭 | 全部计入未读 |
| 一个会话在一个标签页读了 | SSE 广播给所有标签页，所有角标一起清零 |

### 6.4 投递失败与重发

- UDP 没有"连接被拒"可判：发出后 3s 无 `RECVMSG` → 标"未确认"（浅色单勾），8s 仍无 → `failed`（红 `!`）；自动退避重试 3 次（1s/3s/9s），之后只能手动点。
- 对方名册里显示离线时**不盲发**，消息停在 `queued`，界面写"对方离线，上线后自动发送"——这就是飞秋"离线消息"的实际行为（本地排队，不是服务端托管）。
- 幂等：对端按 `packetNo` 去重；重发沿用同一个 `packetNo`，不会产生重复气泡。
- 飞秋 3.0.0.2 的消息缓冲区有"长度声明与实际不符就读到上一条残留"的缺陷，**我们发送时把结尾 `\0` 一并计入声明长度**，避免让对端显示脏数据（见 B.6）。

## 7. 传输层

### 7.1 浏览器 ↔ 宿主（同源，走 DSH 自带 web server）

不另开端口、不碰 CORS，直接复用 DSH 的登录态与回环监听。用 `ctx.webServer.register({ kind, path, handler })` 注册：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/feiq-im/stream` | SSE：`hello`（全量快照）、`roster`、`message`、`receipt`、`error`、`ping`(15s) |
| GET | `/feiq-im/api/bootstrap` | 一次性快照（SSE 不可用时降级轮询） |
| POST | `/feiq-im/api/send` | `{convId, kind, body}` → 返回本地消息（乐观 UI 的确认） |
| POST | `/feiq-im/api/read` | `{convId, upTo}` |
| POST | `/feiq-im/api/retry` | `{msgId}` |
| GET | `/feiq-im/api/history` | `?convId=&before=&limit=50` |
| POST | `/feiq-im/api/settings` | 昵称 / 访问码 / 静音 / 提示音 |
| POST | `/feiq-im/api/scan` | 触发一次网段扫描 |
| GET | `/feiq-im/api/file/:id` | 附件下载（P1） |

SSE 帧形如 `event: receipt\ndata: {"convId":"dm:a|b","upTo":41}\n\n`；`res.flushHeaders()` 后保持写入，`req.on('close')` 时清理。写路由全部校验：Host 为回环地址、`Sec-Fetch-Site` 同源、写操作必须带同源 `Origin`。

### 7.2 宿主 ↔ 宿主：IPMsg 通道（默认，UDP/TCP 2425）

对端无论是飞鸽、飞秋还是另一台本插件，默认都走 IPMsg 标准协议（字段、命令与选项见附录 B 与 B.6）。上层状态机只消费语义事件，不关心字节从哪来：

| IPMsg 事件 | 时机 | 我们做什么 |
| --- | --- | --- |
| `BR_ENTRY 0x1`（广播） | 启动、每 10s、网卡变化 | 宣告在线；收到即入名册并回 `ANSENTRY` |
| `ANSENTRY 0x3` | 收到别人的 `BR_ENTRY` | 回自己的身份（昵称 / 主机名 / 端口） |
| `SENDMSG 0x20` + `SENDCHECK` | 对方发言 | 展示消息，回 `RECVMSG` |
| `RECVMSG 0x21` | 对方收到我们的消息 | `✓ 已送达` |
| `READMSG 0x30`（选项 1） | 对方打开会话 | `✓✓ 已读` |
| `BR_EXIT 0x2` / TTL 超时 | 对方下线 | 灰显"最后在线 HH:mm" |

- 文本消息的**送达回执靠 `RECVMSG`**、**已读回执靠 `READMSG`**，不再依赖 HTTP 200；第 6 节状态机不变，只换事件源。
- 我方发送时同时带 `SENDCHECK` 与 `READCHECK`；对方是老客户端、不回 `READMSG` 时，界面停在"已送达"，不假装已读。

### 7.3 自研 v1 扩展通道（P1，端口 45891，仅本插件互通）

IPMsg 没有群聊、离线投递、加密、大文件断点，这些必须用自己的通道补；只有双方都装了 `dsh-feiq-im` 才启用，UI 不区分（同一会话自动选路）。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/v1/info` | 匿名 | `peerId/nick/host/port/ver/capabilities`，不含密钥、不含绝对路径 |
| POST | `/v1/hello` | 访问码 | 返回 24h token `<随机>.<HMAC>`；同时完成 TOFU 密钥登记 |
| POST | `/v1/message` | token | 落盘 fsync 后返回 200 → 发送方判"已送达" |
| GET | `/v1/poll?after=N&timeout=25` | token | 长轮询收新消息 / 已读回执，250ms 内有数据立即返回 |
| POST | `/v1/read` | token | 上报已读游标 |
| POST | `/v1/typing` | token | 输入中提示（P1） |
| POST/GET | `/v1/upload` `/v1/file/:id` | token | 群聊之外的大文件 / 断点续传（P2） |

- 入站只接受 RFC1918 私网来源，公网 / `127/8` / `169.254/16` 直接拒绝（防 SSRF）。
- 双向都不信任 `from` 字段：`/v1/message` 用 token 持有者身份覆盖，否则同网段任何人都能冒充同事。
- 长轮询够用就不写 WebSocket，真到连接数/延迟成为瓶颈时再评估。

### 7.4 端口与配置

| 用途 | 默认 | 说明 |
| --- | --- | --- |
| UDP 发现 + 文本 | **2425** | IPMsg 标准端口，飞鸽 / 飞秋都认 |
| TCP 文件（飞鸽标准） | 2425 | 协议要求与 UDP 同号 |
| v1 扩展 HTTP | 45891 | 仅本插件之间 |
| 浏览器 ↔ 宿主 | 无独立端口 | 复用 DSH 同源 web server |

2425 被占（**本机开着飞秋**）时不做静默降级：气泡红点，面板顶部出现横幅，按 7.5 的流程处理。

### 7.5 启动检测与"一键关闭飞秋"

启动时，以及运行期间每 30s，执行一次端口体检：

```
尝试绑定 UDP 2425 + TCP 2425
├─ 成功 → 正常模式（气泡右下绿点）
└─ 失败（EADDRINUSE）→ 查占用者
   ├─ 是飞秋 → 横幅（不弹模态，不挡会话）
   │    "本机飞秋正在占用 2425。飞秋和本插件在同事眼里是同一台设备，
   │     同时开会互相覆盖名册，消息可能进错客户端。"
   │    [关闭飞秋并启用]  [仅用本插件网络]  [稍后]
   └─ 不是飞秋 → 只显示 "端口 2425 被 <进程名>(PID) 占用" + [重试]
```

**"关闭飞秋并启用"的执行链（每一环都要能失败降级）：**

1. 确认框列出将结束的进程：`FeiQ.exe · PID 14136 · C:\Program Files (x86)\FeiQ\FeiQ.exe`，用户点确认才动手。
2. `taskkill /PID <pid>`（必要时 `/F`），记日志。
3. 200ms × 10 轮询端口释放；释放后重新绑定，广播 `BR_ENTRY`，横幅消失、气泡转绿。
4. 结束失败（飞秋以管理员身份运行）→ 提示"以管理员身份运行 DSH，或手动退出飞秋"+ [重试]，绝不反复重试杀进程。
5. 记住被杀飞秋的路径，DSH 退出时按用户勾选（默认不勾）**自动重新打开飞秋**，避免"插件把我的飞秋关了还不还回来"。

**安全红线（写进代码注释，不可配置关闭）：**

- 只结束 **PID 既占用 2425、进程名/路径又匹配飞秋签名** 的进程；签名只认 `FeiQ.exe` / `feiq.exe` / `飞秋*.exe` 这类，且路径可读。
- **绝不按端口杀任意进程**，绝不自动杀、绝不静默杀；每次都要一次点击 + 一次确认。
- 用户点"稍后"后 30 分钟不再弹横幅，面板底部保留"修复"入口，不打扰但也不假装没事。
- 运行中飞秋被启动（我们已持有 2425）→ 同样的横幅，但文案改为"飞秋已启动，名册会打架"，同样只提供"关闭飞秋"。
- 以上动作全部写进插件日志（`plugin-data/dsh-feiq-im/log.ndjson`），便于事后追查。

> 备注：理论上"不绑 2425、只用源端口收发"也能和飞秋通信（本机已实测，见 B.6），但飞秋按源 IP 认设备，双开会让同事端的名册在两个端口间来回跳，**所以默认仍然建议二选一**，不提供"错开端口共存"模式。

## 附录 B：与 IPMsg（飞鸽 / 飞秋）互通评估

> 结论：**能互通，值得做**；但飞秋不是"纯标准 IPMsg"，有一层私有扩展头，文件通道更是私有分片。文本互通约 +2.5~3.5 天；文件只保证对飞鸽（标准 TCP）可用，飞秋的文件暂不做。

### B.1 协议事实（已核实）

- 传输：UDP **2425** 收发消息与广播；文件走 TCP，端口与发送方 UDP 端口号相同。
- 标准报文：`ver:packetNo:user:host:command:extra`，`:` 分隔；附加段（引用、文件）用 `\0` 分段。
- 命令：`BR_ENTRY 0x1` / `ANSENTRY 0x3` / `BR_EXIT 0x2` / `SENDMSG 0x20` / `RECVMSG 0x21` / `READMSG 0x30` / `GETINFO 0x40` / `GETFILEDATA 0x60`。
- 选项位：`SENDCHECK 0x100`（要送达回执）、`READCHECK 0x100000`（要已读回执）、`BROADCAST 0x400`（群发）、`FILEATTACH 0x200000`、`ENCRYPT 0x400000`。
- **飞秋 3.0.0.2 不是纯标准格式**：抓包样本是 `1_lbt6_0#128#001122334455#0#0#0#4001#9:1792156361:USER:PC-NAME:0:<消息>\0` —— `#` 之前是飞秋私有的 8 字段扩展头，`:` 之后才是 IPMsg 段（详见 B.6）。

参考：[命令常量表](https://api.metacpan.org/v1/source/MASANORIH/Net-IPMessenger-0.14/lib/Net/IPMessenger/MessageCommand.pm)、[协议翻译](https://www.cnblogs.com/hnrainll/archive/2011/05/07/2039567.html)、[文件传输说明](http://www.cppblog.com/Panda/archive/2010/01/11/105406.aspx)、[飞秋 3.0.0.2 协议逆向](https://moxin1044.github.io/posts/fe1a/)。

### B.2 为什么和我们的模型天然对得上

| IPMsg 事件 | 我们的 UI |
| --- | --- |
| `BR_ENTRY` / `ANSENTRY` | 名册里立刻出现（**零添加**） |
| 超时无音信 / `BR_EXIT` | 离线灰显 |
| `SENDMSG`（文本） | 消息气泡 |
| `RECVMSG`（我们发时带 `SENDCHECK`） | `✓ 已送达` |
| `READMSG`（带 `READCHECK`） | `✓✓ 已读` |
| `SENDMSG + BROADCAST` | 群发（全员广播） |
| `FILEATTACH` + `GETFILEDATA` | 文件传输（仅飞鸽标准；飞秋私有分片见 B.6） |

也就是说，第 6 节那套状态机不用改，只是把"HTTP 200 即送达"换成"收到 `RECVMSG` 即送达"，"收到 read 帧"换成"收到 `READMSG`"。

### B.3 端口策略：绑 2425，与飞秋二选一

早先设想的"用高位端口绕开 2425"对标准 IPMsg 成立（对端按来源地址回包），但**飞秋把源 IP 当设备身份**，且它的回包与文件端口行为没有公开文档。所以策略改成：

- **默认绑 UDP 2425 + TCP 2425**，兼容性最好。
- 2425 被占（本机开着飞秋）时不做"错开端口共存"的幻想：同一源 IP 在飞秋眼里只有一台设备，双开只会互相覆盖名册与回执。UI 明确提示"与飞秋二选一"，并提供"仅 v1 通道"模式（只和装了本插件的机器互通）。
- "高位端口 + 源端口回包"留作实测通过后的可选模式，默认不开。

### B.4 工作量

| 项 | 天数 | 说明 |
| --- | --- | --- |
| 报文编解码 + GBK/UTF-8 | 0.5–1 | 解码用内置 `TextDecoder('gbk')`（已实测）；编码用启动时反推的 23,939 字映射表（已实测，毫秒级），零依赖 |
| 标准段 + 飞秋 `#` 扩展头解析 | 0.5 | 两种格式都要吃；发送先用标准段，真机验证是否要补扩展头 |
| 名册 / 在线状态（ENTRY/ANSENTRY/TTL） | 0.5 | 飞秋按源 IP 去重，需按此适配 |
| 文本收发 + 送达/已读映射 | 0.5–1 | 状态机复用，只换事件源 |
| 端口与身份二选一 + 提示 | 0.5 | B.3 |
| **文本互通小计** | **2.5–3.5 天** | 含一轮真机联调 |
| 文件（飞鸽标准 TCP） | 2–3 天 | 只对飞鸽 / 标准实现 |
| 飞秋文件（私有 UDP 分片） | 3–5 天 + 高风险 | 公开资料只逆出一部分，建议不做 |
| 真机联调（飞鸽 / 飞秋 / 手机 IPMsg） | 1–2 天 | 需要一台装飞秋的机器或虚拟机 |

净增约 2.5 天（相对自研协议），换来"同事不用装插件也能聊"，而且**拿到飞秋就能立刻验证**。

### B.5 互通做不到的（仍要我们的 v1 通道）

- 群聊：IPMsg 只有广播/组播，没有"群"；群聊留在 v1。
- 离线消息：对端不在线就没有投递点，只能本地排队等他上线（和飞秋行为一致）。
- 历史同步、加密、大文件断点、输入中提示：v1 扩展。
- **图片、飞秋的文件分片**：私有协议，不做。
- 已读回执在部分老客户端不生效（不支持 `READCHECK`）→ 界面上降级为只显示"已送达"，不假装已读。

### B.6 飞秋兼容性核对（逐项）

依据：对 FeiQ 3.0.0.2 的公开逆向与实测（[末心：飞秋协议缺陷分析](https://moxin1044.github.io/posts/fe1a/)），样本为 2013 年构建；现网版本可能更老或更新，最终以真机联调为准。

| 能力 | 飞鸽（标准） | 飞秋 3.0.0.2 | 我们的处理 |
| --- | --- | --- | --- |
| 发现 / 名册 | ✅ `BR_ENTRY` / `ANSENTRY` | ✅ 但带 `#` 扩展头；**按源 IP 去重** | 两种格式都解析；名册按源 IP 适配 |
| 文本 | ✅ | ✅ | P0 双向 |
| 送达回执 | ✅ `RECVMSG` | ✅ | `✓` 单勾 |
| 已读回执 | ✅ `READMSG` | ✅ | `✓✓` 双勾 |
| 群发 | ✅ `BROADCAST` | ✅ | P1 |
| 文件 | ✅ TCP `GETFILEDATA` | ⚠️ 私有 UDP 分片（命令 0x7F 分支），字段未完全公开 | 只做飞鸽；飞秋不做 |
| 图片 | ❌ | ⚠️ 私有分片 | 不支持 |
| 加密模式 | ❌ | ⚠️ `ENCRYPT` | 不支持，收到直接提示 |
| 群聊 | ❌ | ⚠️ 广播 / 组播扩展 | 走 v1 通道 |

**四条必须遵守的细节：**

1. **`#` 扩展头**：飞秋报文 `#` 之前最多 8 个字段（`1_lbt6_0#128#MAC#0#0#0#4001#9`）。解析时先按 `:` 切段，再容忍首段里带 `#`；**不要**因为 `ver != "1"` 就丢包——否则飞秋的包全被丢掉。
2. **长度字段要含 `\0`**：飞秋按第二字段（样本里的 `128`）声明的字节数拷贝，且不补终止符——声明少了，它会把上一条消息的残留当正文显示。我们**发送时把 `\0` 计入长度**。
3. **按源 IP 认设备**：一台机器 = 一个设备，换端口不算新设备。这决定了 B.3 的"二选一"，也意味着**同一台机器不能同时跑飞秋和本插件**。
4. **未知命令静默忽略**：飞秋会回 `217:<MAC>` 之类的私有握手和 0x7F 分片。解析失败一律丢弃并计数，绝不抛异常、绝不影响文本通道。

**本机实测记录（2026-11-20，本机正在运行飞秋）**

1. 向本机 2425 发**纯标准格式**的 `BR_ENTRY`：`1:1000001:DSH-PROBE:DSH:1:\0`，五个本地地址各回一包：
   `1_lbt80_0#128#001122334455#0#0#0#4000#9:1795120395:Tester:PC-TEST:6291459:²âÊÔÔ±\0\0`
   - 飞秋**接受不带 `#` 头的标准请求**；回包带 `#` 私有头；
   - 第二段是 **epoch 秒**（`1795120395`），不是递增序号；
   - 命令 `6291459` = `0x600003`（模式 3 = ANSENTRY + `0x600000` 标志位）；
   - extra 是 **GBK** 状态串，结尾两个 NUL。
   - 版本串是 `1_lbt80_0`（那篇逆向文章里是 `1_lbt6_0`）——**不要依赖该字段的值**。
2. 向本机飞秋发 `SENDMSG|SENDCHECK|READCHECK`（`1048864` = `0x100120`）：
   `1:1795164632:DSH-PROBE:DSH:1048864:probe-from-dsh 1795164632\0`
   飞秋回 `...:33:1795164632\0` → `33` = `0x21` = **RECVMSG**，extra 回显我们发的 packetNo。
   - **送达回执链路成立**，且请求用的是纯标准格式。
3. 待人工确认：`READMSG`（已读）需要真人打开消息窗口才会回，自动化测不出来；文件同理需要真人点接收。

结论：**文本 + 送达可以先按"标准格式发送、双格式接收"实现**，飞秋这条链路不需要我们先伪造它的私有头；已读回执留到真机人工验证。

**安全边界（重要）：**

- 飞秋 3.0.0.2 的文件/图片分片存在**未校验偏移的远端堆溢出**，消息缓冲还有**跨会话残留**（把上一条消息的尾巴显示给下一个人）。我们**不实现它的分片入口**、**不发送畸形长度**，入站所有长度/偏移先做区间校验——既不给人递刀，也不让自己成为攻击面。
- 明文、无认证：和飞秋一样，同网段抓包可见。别用它传凭据。

### B.7 建议

传输层两条通道：**IPMsg（默认：发现 + 文本；飞鸽文件）** + **v1（扩展：群聊、离线队列、加密、大文件）**。P0 先交付 IPMsg 文本互通——拿到一台装飞秋的机器就能验收。

## 附录 C：飞秋 3.0.0.1 的闪屏 / 文件 / 图片（本机实测）

### C.1 版本与配置

- 运行进程：`C:\Users\Tester\Downloads\FeiQ.exe`，FileVersion **3.0.0.1**（同目录另有一份 3.0.0.2，未运行）。
- `C:\Program Files\feiq\FeiqCfg.xml`：`Version=4000`、`IPMsgCompatible=1`、`ShakeMsgTip=1`、`BmpUdpSendSize=512`、`BmpUdpTrys=10`、`AutoRecvFile=0`。
- UDP/TCP **2425** 都由它持有。

### C.2 封装

- `ver:packetNo:user:host:cmd:extra` + 结尾 `\0`；ver 用 `1_lbt80_0#128#<MAC>#0#0#0#4000#9`。
- **user/host 里的 `:` 要换成 0x08**，否则字段被切断（收包时再换回来）。
- 未知命令静默忽略：实测它会发 `0x1D8(472)`、`0xD9(217)`、`0x77(119)`。

### C.3 闪屏震动 —— 已实测成功 ✅

- 命令 **0xD1（KNOCK）**，extra 为空。
- 实测：向本机 `2425` 发一条 0xD1，**这台飞秋窗口真的抖了**，并回 `0xD2(210)` 确认；同时收到 `0xD9`（回显我们报的 MAC）、`0x77`、`0x1D8`。
- 实现：`buildKnockPacket()` 已落地；收 0xD1 → UI 闪屏；按人节流 5s 防骚扰。

### C.4 文本

- `SENDMSG|SENDCHECK`（`0x120`），GBK，可带 `{format}` 后缀；明文，无加密（参考实现与实测均如此）。
- 回执：`RECVMSG(0x21)` 送达、`READMSG(0x30)` 已读。

### C.5 文件

- 报价：`SENDMSG|FILEATTACH`（`0x00200020`），extra = 文本 + `\0` + 条目 + `0x07`。
- 条目：`id:name:sizeHex:mtimeHex:typeHex:`；文件名里的 `:` 写成 `::`；多文件条目之间用 `0x07`。
- 下载：接收方连发送方 **TCP 2425**，发一个标准包，命令 `GETFILEDATA(0x60)`，extra = `报价packetNo:fileId:offset:`（**全十六进制**）；随后服务端裸流 2KB 一块，无长度头。
- 因此**接收文件必须监听 TCP 2425** → 与飞秋二选一（正好由 7.5 的"一键关闭"处理）。

### C.6 图片 —— 已抓包解析 ✅

本机抓了一次真实发送（WLAN、`udp port 2425`、83 包，其中 36 个图片分片、32 个重传请求），格式如下：

```
extra = "<id>|<total>|<offset>|<chunks>|<index>|<chunkLen>|0|<code>|0|00000000#" + \0 + <data>
```

| 字段 | 含义 |
| --- | --- |
| `id` | 8 位十六进制，每张图一个（发送方生成） |
| `total` | 图片总字节数 |
| `offset` | 本片在图片里的字节偏移 |
| `chunks` | 总分片数 |
| `index` | 分片序号，**从 1 开始** |
| `chunkLen` | 本片字节数（最后一片是短的） |
| `code` | **2 = JPEG**，**1 = 飞秋自有的 `LZW!` 容器** |
| `data` | `#` 后紧跟**一个 NUL 填充**，再是原始字节 |

- 命令：`SENDIMAGE(0xC0) | FILEATTACH(0x200000)`；**整包不带结尾 NUL**（数据按 `chunkLen` 截取）。
- 分片大小：**512** 字节（`BmpUdpSendSize`），最后一片按实际长度。
- 重传：接收方对需要的分片发 `0xC1`，extra = `<id>|<index>#`；发送方收到就重发该片（`BmpUdpTrys=10` 次上限）。
- 验证：按上述规则把 20 个分片拼回来，得到一张 **JPEG 484×375**，SOI/EOI 完整、能正常打开——就是我们抓包时你发的那张截图。
- 收图侧还要处理 `code=1` 的 `LZW!` 容器（飞秋对部分图片会先压缩），这块单独实现。

**发送（已实测通过 ✅）**

飞秋对"不支持公钥"的对端会发**明文图片消息**，格式是两步：

1. 先发一条 `SENDMSG|SENDCHECK`，正文是图片占位标记：
   `/~#><8位id><B~{/font;-16 0 0 0 400 0 0 0 134 0 0 2 32 微软雅黑 8404992;}`
2. 再发 `0xC0` 分片，`id` 与上一步一致，`code=2`（JPEG）。

**两条硬约束：**
- 图片消息和分片都必须带飞秋的 `#MAC` 私有头（`1_lbt6_0#128#AABBCCDDEEFF#0#0#0#4001#9`），否则飞秋只回 `RECVMSG`、一个分片都不请求（第一次试验就是这么失败的）。
- `0xC1` 是**分片确认**，不是重传请求。收到确认后**绝不能重发**，否则两边乒乓成环——我们一度 15 秒刷了 8 万个包。未确认的分片按定时器补发（`BmpUdpTrys=10`）。

实测：给本机飞秋发一张 9769 字节 JPEG，20 个分片全部确认、**0 次补发**，飞秋正常弹出图片。

### C.7 顺带发现：飞秋的加密是可选的

抓包里看到 `0x72/0x73`（`GETPUBKEY`/`ANSPUBKEY`）和两条 `0x400120`（`SENDMSG|SENDCHECK|ENCRYPT`，128 字节加密密钥 + 80 字节密文），说明**双方都支持公钥时**飞秋会加密文本。

但对"不回应公钥请求"的对端（我们的 `DSH-IM` 假设备），飞秋**整场对话都是明文**：`ANSENTRY`、`SENDMSG`、图片占位标记、图片分片，全部可读可解析。

结论：我们不实现公钥，就不会被加密：
- 我们发飞秋：明文，飞秋正常显示（已实测：文字 ✅、图片 ✅）；
- 飞秋发我们：明文，能解析（已实测：文字、图片、抖动）。
